# AgentGauge v0.1.0 Feature Lock

**Status:** Scope frozen; launch approval is still pending the release gates below.

**Version basis:** `0.1.0` is the value currently present in `app/src-tauri/tauri.conf.json`, `app/package.json`, and `app/src-tauri/Cargo.toml`. This document does not assert that a public v0.1.0 tag or release already exists.

**Purpose:** Record what belongs in the first launch, what is explicitly not part of it, and how to prevent later feature work from delaying or destabilizing that launch.

## Lock rule

From this lock onward, **no new feature, enhancement, broad refactor, or unrelated dependency change enters v0.1.0**. New work goes to the next-version backlog; its version number is not assigned until the release owner chooses it. A task's existence, a roadmap proposal, or an implementation in a working tree does not add it to the locked release.

Only these changes may be considered for v0.1.0:

- A reproducible release-blocking defect in a locked feature.
- A security, privacy, data-loss, or serious correctness fix.
- A required packaging, signing, installation, or compatibility fix for a platform actually advertised for v0.1.0.
- A correction needed to remove a materially false product or safety claim.

Every exception requires explicit release-owner approval before implementation. Record the decision here before merging: reason, affected locked feature, risk/rollback, tests, and whether version metadata or customer-facing claims change. Keep the fix isolated. Anything else goes to the next version. Do not silently widen the lock or change the release version to make unfinished work appear included.

## Implemented v0.1.0 scope

These capabilities are present in the current implementation. “Implemented” does not mean every release gate has passed.

| Area | Included behavior | Boundary / evidence status |
| --- | --- | --- |
| Desktop app and onboarding | Tauri desktop app, onboarding, settings, and local durable state. | Packaged release still needs native launch/smoke verification. |
| Codex usage | Reads reported five-hour and weekly usage windows and reset information through the locally installed `codex app-server`; reports freshness and availability; observes changes in reported `resetsAt`. | A changed reset value is an observed signal, not proof that a rollover has occurred. No provider window is manufactured. |
| Connected coding plans | Reads supported Codex and OpenCode-connected Z.AI, MiniMax, and Kimi plan data; separates the source and failure/unavailable states. OpenCode supplies local plan/model discovery and credentials for supported coding-plan requests. | This is not a general native OpenCode usage-window integration. Supported providers and endpoint behavior are narrower than the harness list in the PRD. |
| Rollover monitors | Read-only per-connection monitors with persisted choices and a Home status glance. | Monitoring does not trigger or reset a provider window and is separate from quota-consuming kickoff. |
| Scheduled kickoff | Explicit per-connection opt-in for supported connections; a small `Hi` action, model/effort selection where exposed, attempt/status history, and macOS background scheduling. | The current scheduler follows the latest reported reset; it does not verify rollover and may attempt immediately when no reset is available. A prompt spends quota. Do not call this verified-rollover automation or run a live send as a release test without explicit user approval. |
| Stats | Local analytics for supported plans, including available Codex/OpenCode activity histories and provider-reported plan/model data; per-source time span and API-equivalent cost estimates. | Sources cover different periods. Cost is an estimate, not a bill or proof of subscription consumption; values must not be summed across incompatible spans. Current analytics are on by default and have no in-app opt-out. See the policy decision below. |
| Processes | Read-only process/resource, port, and local-storage information for the tracked toolchain. | No stop, signal, or delete operations. Available process/port details vary by platform. |
| macOS system widget | WidgetKit extension with usage snapshots, built and embedded by the macOS build workflow; the user adds it from the system widget gallery. | The app cannot install it or detect placement. The current documented environment has not confirmed that it appears in the gallery; do not promise gallery availability until manually verified. |

## Explicitly outside v0.1.0

- Pi, Claude Code, Kilo Code, and other new harness integrations.
- A complete/native OpenCode harness capability matrix or universal OpenCode subscription-window reader.
- Verified-rollover kickoff, catch-up sends, or any action that claims to cause/reset/extend a window.
- Multi-account profiles, identity switching, or per-account automation.
- Windows/Linux release claims, background scheduling, or widget parity. macOS is the only exercised platform.
- Cloud synchronization, hosted analytics, or a hosted backend.
- New analytics sources, broader history coverage, or more cost/usage calculations beyond the implementations already present.
- New analytics visualizations, including a day-by-day activity heatmap.
- In-app credential entry, credential ownership, or sign-in automation.

Bug fixes and truthful copy changes within the locked behavior are not scope expansion, subject to the exception rule if they affect release behavior.

## Decisions required before publishing

These are discrepancies between the current implementation and the PRD's stated target behavior. The release owner must explicitly accept the v0.1.0 behavior and align the product documents, or treat the discrepancy as a blocker and remove/disable the affected claim or capability. Do not silently resolve a policy mismatch by changing scope during feature freeze.

1. **Local analytics permission:** The current app reads local usage/activity sources by default and has no in-app opt-out. The PRD describes separate explicit permission before local history access. Accept this v0.1.0 behavior and update the product promise, or block/disable the affected local-history analytics until permission behavior is resolved. Do not describe the current behavior as separately permissioned.
2. **Provider coding-plan requests:** For supported OpenCode-connected plans, the app makes documented provider coding-plan requests using credentials managed by OpenCode. The PRD's broad “no direct provider API” language does not describe this implementation. Confirm and document the approved boundary and provider terms; the app must not solicit, persist, or manage those credentials.
3. **Kickoff eligibility:** Current scheduling follows reported reset times without verifying a new window, while the PRD's target requires a verified rollover. Accept and label the current limitation, or disable scheduled kickoff for launch until eligibility satisfies the target. A prompt consumes quota and must never be described as causing a reset.
4. **Widget availability:** The extension build, bundle structure, signature check, and snapshot contract have evidence, but gallery appearance is not verified in the current environment. Manually verify before advertising an available system widget; otherwise document the limitation and omit that claim.
5. **Documentation accuracy:** The current README says OpenCode's usage history is not read, while the implementation now reads OpenCode's local session database for analytics. Reconcile this and the other current-versus-planned statements in the README/PRD before publishing; do not leave user-facing documentation contradicting the shipped data sources.

These decisions are **not authorization to add features**. If resolving one requires new behavior, use the release exception rule or defer that behavior to the next version.

## Release gates

The release is not cleared until each applicable gate is checked and evidence is recorded in the release notes or release checklist.

- [ ] **Scope:** No unapproved feature has entered v0.1.0; active implementation tasks are either explicitly included as locked bug fixes or moved to the next-version queue.
- [ ] **Version:** `tauri.conf.json`, `app/package.json`, and `app/src-tauri/Cargo.toml` agree on the intended release version. The current values are all `0.1.0`.
- [ ] **Policy:** The five decisions above have explicit release-owner outcomes, and README/PRD/roadmap claims agree with those outcomes.
- [ ] **Build and tests:** Run the frontend build/unit suite and Rust formatting, tests, check, and clippy gates required by the repository rules. Run the feature e2e specs against the real compiled app for the changed/launch-critical surfaces; record exact commands, results, and platform.
- [ ] **Outstanding e2e status:** The task registry's latest recorded full run was 42 passing / 13 failing, and multiple focused UI tasks were blocked on the embedded WebDriver. Re-run after those investigations close; a blocked or partial run is not a pass.
- [ ] **macOS artifact:** Build the actual release artifact with `cd app && bun run build:mac` so the WidgetKit extension is included. Launch the packaged app and smoke-test onboarding, usage reads, navigation, and the selected v0 scope. Record macOS and Xcode versions.
- [ ] **Widget claim:** If the widget is advertised as available, manually confirm it is discoverable in the system widget gallery and renders a current snapshot. The app must not claim it placed or detected the widget.
- [ ] **Other platforms:** Either publish/claim macOS only, or provide independent build, install, and behavior evidence for each additional OS. `bundle.targets: "all"` is not verification that every target is supported.
- [ ] **Quota safety:** Verify opt-in defaults and configuration/stop behavior without sending a real prompt. A live send spends quota and requires separate, explicit authorization.
- [ ] **Distribution:** Record the actual artifact formats, signing/notarization state, installation path, and any unsupported OS versions. Do not infer signing, notarization, auto-update, or widget-gallery availability from a successful compile.

## Version and release research

Context7 research consulted the official Tauri v2 documentation (`/tauri-apps/tauri-docs`):

- Tauri's v2 configuration supports an app version as a SemVer string or a path to a `package.json` containing `version`; if omitted it falls back to the Rust package version. The documentation recommends managing the app version in Tauri config. This project currently hard-codes the same `0.1.0` in three files, so release bumps must deliberately keep them aligned. See [Tauri distribution: versioning](https://v2.tauri.app/distribute/) and the [Tauri config version definition](https://github.com/tauri-apps/tauri-docs/blob/v2/packages/tauri/crates/tauri-utils/src/config.rs).
- Tauri distribution instructions are platform-specific and note platform/version constraints. A configured bundle target list or successful build on one host is not evidence for other OSes, signing, or installer readiness. See the [Tauri v2 distribution guide](https://v2.tauri.app/distribute/) and [Windows installer guide](https://v2.tauri.app/distribute/windows-installer/).
- This is upstream release/version guidance, not a source of product scope. The locked features, platform claims, required checks, and exception policy above are project decisions based on this repository's configuration, README, PRD, current implementation, and testing rules.
